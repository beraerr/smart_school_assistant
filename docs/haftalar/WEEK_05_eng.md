# Week 5 — Intent Detection, Explainability and Hardening

**Project:** Smart School Information System
**Previous state:** Week 4's working `/query` endpoint (`week5/week-05/`, a copy of Week 4)

---

## 1. Goal of this week

In Week 4, `/query` worked, but it treated every question as an SQL query and
sent it to Claude — even someone typing "hello" got pushed through the SQL
generation process unnecessarily. This week adds three things: intent
detection that figures out whether a question is actually a data query or
just chat, a short explanation alongside the result, and hardening against
misuse via rate limiting and logging. No new endpoint — the existing `/query`
matures.

## 2. Deliverables

- [ ] `backend/app/services/intent_service.py` —
      `detect_intent(question: str, client=None) -> Literal["chat", "sql"]`;
      the `client` parameter is optional, for testability (dependency
      injection)
- [ ] `backend/app/services/explain_service.py` —
      `build_explanation(role: str, related_class: str | None, related_id:
      int | None, row_count: int) -> str`; rule-based, makes no LLM call
- [ ] `backend/app/core/rate_limiter.py` — a 60-second sliding-window limit
      of 10 requests per user, in-memory; returns `(False,
      retry_after_seconds)` when exceeded
- [ ] `backend/app/core/logging_config.py` — a JSON-formatted log handler
- [ ] `query.py` update: check rate limit first → then detect intent →
      `chat` gets a short reply, `sql` goes through Week 4's full pipeline
      plus an explanation → every request ends with one JSON log line
- [ ] Unit tests for the three new services (no API key needed for the rate
      limiter and explain_service at all; intent_service uses a mock client)

## 3. Out of scope (deliberately deferred)

- Streamlit interface → Week 6
- Shortcut/pattern-matching layer (fast response before the LLM) → Week 7
- A shared rate-limit store like Redis → out of scope (a known limitation
  stated in the README)
- Separate intent categories beyond the chat/sql binary split

## 4. Acceptance criteria

1. Sending `{"question": "hello"}` returns a friendly reply without ever
   touching the database.
2. Sending `{"question": "how many students are in my class"}` goes through
   Week 4's full pipeline (Claude → safety → RuleEngine).
3. When the same user makes an 11th request within 60 seconds, it returns
   `429 Too Many Requests` with a `Retry-After` header in the response.
4. Every `/query` request (successful or not) leaves a single-line JSON
   entry in the server logs.
5. The body of an SQL-intent response contains an `explanation` field, and
   that field is based on the filter `RuleEngine` applied (not generated by
   the LLM).
6. `rate_limiter.py` and `explain_service.py` tests run and pass without
   `ANTHROPIC_API_KEY`.
7. `intent_service.py` tests use a mock client to verify both the `chat` and
   `sql` branches without an API key.

## 5. Demo flow for the presentation

1. Send `{"question": "Hi, how are you?"}` — show a friendly reply coming
   back, and show in the server logs that `"intent": "chat"` was logged and
   the database was never touched.
2. Send `{"question": "How many students are in my class?"}` — show that the
   response contains both a `results` field and an `explanation` field.
3. Run a short loop sending 11 requests in a row, show that the 11th returns
   `429` with a `Retry-After` header.
4. Tail the server logs with `tail -f` and show each request leaving a
   single JSON line live.

## 6. Notes / rationale

- The rate limiter being in-memory is a deliberate limitation — fine for a
  single-worker development environment; the README explicitly states that
  production would need a shared store (Redis, etc.).
- Generating the explanation text with rules instead of the LLM is a
  deliberate design decision to eliminate the risk of Claude saying
  something inconsistent or wrong while "explaining" its own result
  (hallucination).
- No new dependency was added this week — rate limiting and logging were
  written with Python's standard library, and intent detection reuses the
  existing `anthropic` SDK.
